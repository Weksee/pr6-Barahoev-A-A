# DECISIONS.md

## Вариант

Номер варианта: 3 

Часть А: правило R4 (FAST_TRACK) теперь срабатывает только при
`urgent == true` И `amount < 100 000`. Срочные заявки с суммой
100 000–499 999 уходят в STANDARD (или в FINANCE_REVIEW, если ≥ 500 000).

Часть Б: добавлен метод `addUrgencyFlag(long amount, boolean urgent)`,
возвращающий true, если заявка действительно срочная и подлежит
ускорению (urgent && amount < 100 000).

## Решение 1

Формулировка: порог ускорения вынесен в отдельный метод
`addUrgencyFlag`, а не написан инлайн в `route`.
Альтернатива: писать условие `urgent && amount < 100_000` прямо в route.
Обоснование: изменение варианта локализовано в одном методе; при
следующем изменении порога правится только `addUrgencyFlag`, а не
весь route.

## Решение 2

Формулировка: проверки R1–R5 идут строго в порядке приоритета:
personal → HIGH → сумма → срочность → STANDARD.
Альтернатива: объединить условия в одно большое выражение.
Обоснование: последовательные `if` с ранним return делают приоритет
наглядным и совпадают с Activity-диаграммой; легче объяснить
пересечения (personal > HIGH > сумма > срочность).

## Ответы на контрольные вопросы

### Вопрос 1
Наиболее вероятная ошибка — неверный порядок проверок: если поставить
проверку срочности (R4) раньше проверки персональных данных (R1),
срочная заявка с персональными данными уйдёт в FAST_TRACK вместо
SECURITY_REVIEW. Защищает последовательность if в методе
`ApprovalRouter.route`: R1 (containsPersonalData) проверяется первой,
до R2–R5, и сразу возвращает SECURITY_REVIEW.

### Вопрос 2
Ключевое бизнес-правило — приоритет маршрутов R1 > R2 > R3 > R4 > R5 —
содержится в методе `route` класса `ApprovalRouter`. Это единственная
точка бизнес-логики маршрутизации; метод нестатический, без состояния,
легко тестируется. Порог финансового контроля вынесен в константу
`FINANCE_LIMIT`, что позволяет менять его без правки логики.

### Вопрос 3
Ромб «R4: urgent && amount < 100_000?» на Activity-диаграмме
соответствует строке `if (addUrgencyFlag(amount, urgent))` в методе
`route`. Если условие истинно — возвращается `FAST_TRACK`, иначе
управление переходит к `STANDARD`. При изменении порога в
`addUrgencyFlag` меняется только эта ветка.

### Вопрос 4
Изменение значения `FINANCE_LIMIT` (например, с 500 000 на 250 000)
затронет только класс `ApprovalRouter` и только константу. Логика
`route` не меняется, потому что порог используется через константу.
Это соответствует принципу единой точки изменения: один класс, одна
константа, остальные классы (`ApprovalRoute`, `RiskLevel`, `SelfCheck`)
не затрагиваются.

## Фрагмент кода для анализа

Фрагмент `if (urgent) return FAST_TRACK; if (containsPersonalData) return
SECURITY_REVIEW;` нарушает приоритет правил: срочная заявка с
персональными данными (urgent=true, containsPersonalData=true) уйдёт в
FAST_TRACK, хотя по правилам R1 (personal) имеет высший приоритет и
должна вернуть SECURITY_REVIEW. Исправленный порядок: сначала проверка
`containsPersonalData`, потом `urgent`.
